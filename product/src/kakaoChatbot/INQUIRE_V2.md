## LLM 필요성
### 필요성 1.
티커를 정확히, 게다가 야후파이낸스 스타일로 입력하는 것은 나쁨.  
다음과 같이 검색할 수 있어야 함.

```
"애플"
"삼전"
"환율"
"금리"
"아이폰"
"버거킹"
```

시간에 덜 민감하고 명확하게 티커와 검색어가 1:1 매칭될때 검색어로부터 티커(또는 티커들)를 연상해내기.

<br>

유저들은 다음과 같은 질문들을 많이 함. 이것이 일반적으로 챗봇에 유저들이 기대하는 바. (피드백)

```
"가장 비싼 주식 뭐야?"

"AI 기업"

"배당주"
```

### 로직

카카오톡 쳇봇 타임아웃 기준 내에 로직이 안정적으로 수행되는것을 기대하기 위해  
캐시를 읽는 IO(위 (2), (3) 에 해당)는 각 로직 단계에서 동기적으로 연결됨을 허용하나,  
HTTP IO(위 (4), (5)에 해당)는 불필요한 IO 가 발생할 지라도 몇몇 지점에서 병열로 수행할 필요가 있음.

특히, Market 에서 ticker 가 존재하지 않을떄 Notfound 를 던지기까지 IO 가 2000~4000 소요.  
이 IO 의 성능을 개선할 필요가 있으나, ((9) 를 새로 만들고 병열로 처리하여 약간의 개선을 함. 더 개선이 필요.)  
우선, 이 IO 를 최대한 피하고 (검색어가 티커타입인지를 잘 검사하는 것 만으로도 큰 효과 예상)  
로직을 중첩시켜 다른 IO 와 병열 처리를 허용하겠음.  

최후의 수단으로, 타임아웃 발생시 재시도를 유도하고  
재시도가 일괄처리 및 캐싱으로 이전 타임아웃 요청과 열결성을 가지도록 하겠음.

```

          N ______________________ Y
          |                        |

  ticker 어레이 찾음?             asset 읽음?
 Y ______________ N          Y ___________ N
 |                |          |             |
 |                |          |             |
(A) - iter       (B)      응답(OK)         (3)
               응답(OK)               ticker 어레이 찾음?
                                 Y _________________ N
                                 |                   |
                                 |                   |
                                (A) - iter        (4) - 캐싱 및 일괄처리
                               응답(OK)            t(ms) 기다림
                                                  (B) 병열수행
                                                  (4) (B) 중 먼저 성공하는 것으로 응답
                                                  둘다 실패하면 (B)의 실패로 예외던짐
```

## Issues

### # 경쟁하는 Promises
구현에서 Market 이 NotFound 에셋을 더 빨리 찾기위해서, (Market > AccessorService.subscribeAssetAndGet)  
그리고 Inquire_V2 로직상 최종적으로 쿼리를 티커로 다룰지 모델에 쿼리할지 모를때 둘 모두를 경쟁시키는 부분에서 (Product > KakaoChatbotService.inquireAsset_v2)  
각각 먼저 성공하는 비동기 응답을 사용하고 나머지는 버려질 떄가 있음.

이 버려지는 비동기 작업을 적절히 취소하면 좋을지 고민했고 결론을 기록하겠음.

<br>

#### > 결론: 일단 지금은 취소할 필요를 못느끼기에 그대로 둠.
버려진 프로미스도 백그라운드에서 나름 의미있는 작업을 수행함.

만약 취소한다고 하면 목적에서 버려진 시점에 즉시 취소를 해야 의미가 있음.
그러나 여기에는 꽤나 까다로운 문제가 있음.

<br>

#### > 프로미스의 즉시 취소에 대해서...
한번 프로미스가 큐(마이크로테스크큐)에 들어가면 외부에서 취소시키거나 꺼낼 방법이 없어보임.

즉시 취소를 하려면 프로미스를 만들때 미리 거부 함수를 꺼내좋는 방법밖에 없어보임.

이런 즉시 취소는 범용성이 너무나도 떨어진다고 판단됨.

<br>

#### > 프로미스의 즉시 취소 구현의 범용성 문제

1. Async 함수를 사용하기 까다로와짐.  
즉시 취소할 거부 함수를 미리 꺼내두는 문제 때문.

2. 프로미스의 깊이 문제.  
프로미스 내부에서 호출할 가능성이 있는 다른 모든 프로미스에 대한 거부 함수를 만들어서 미리 빼놔야하는가?

3. 취소 시점의 문제.  
취소하고 싶은 프로미스가 어떤 로직인지, 그리고 취소 시점에 그 프로미스가 어느 단계까지 실행되었는지에 따라 취소 로직은 매우 달라질 수 있음.

이렇게 범용성이 없는 기능은 필요하면 안된다고 판단함.  
이런것이 필요한 구현은 이미 좋은 구현이 아닐수 있으며,  
차라리 이런 고민을 하게 만든 구현을 개선해서 고민을 제거하고 싶음.  
또는 지금 구현이 의도한 그대로라는 결론이 있음.

나는 일단 후자를 결론으로 택하지만  
테스트할때  
"Jest did not exit one second after the test run has completed."  
라는 노란 경고는 옳지 않기에 이 이슈는 좀 더 고민해보자.
